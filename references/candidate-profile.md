### Platform Debugging and Kubernetes Exposure

Core story: During AI Single Entry Point work, I went beyond frontend debugging to inspect the Kubernetes/service layer with platform engineers and help isolate an integration issue.

Context:
- The AI Single Entry Point needed to call a 3D image classification service.
- The issue was not obvious from the frontend. The service existed, pods were running, but the integration was not behaving as expected.

What I checked:
- Used `kubectl get pods -o wide` to confirm pods were running and inspect IP/node placement.
- Used `kubectl get service -o wide` to inspect service type, cluster IP, external IP, port, and selectors.
- Used `kubectl describe pod` to inspect containers and exposed ports.
- Used `kubectl exec` and `/proc/net/tcp` to check which port the container was actually listening on.
- Used `kubectl port-forward` to connect local port to the pod port.
- Used `curl` and `telnet` to verify TCP connectivity and distinguish "port unreachable" from "protocol mismatch."

Finding:
- The port was reachable, which meant the issue was not simply pod down/service unavailable.
- The behavior suggested a protocol mismatch: the service used `TBufferedTransport + TBinaryProtocol`, while Jukwaa expected `TFramedTransport + TBinaryProtocol` or staging strict binary behavior.
- Follow-up required changing service config and service-registry settings.

Technical depth to mention:
- Kubernetes service discovery and ClusterIP behavior.
- Difference between pod port, service port, target port, and load balancer exposure.
- Port-forwarding as a debugging tunnel.
- Thrift transport/protocol compatibility as an integration failure mode.

Impact / evidence:
- Helped narrow a broad integration problem into an actionable platform/backend configuration issue.
- Demonstrated ability to work with platform engineers and reason about runtime infrastructure.
- Strengthened 3D/AI story by showing ownership beyond UI and GraphQL code.

How to tell it:
- Use this when asked about debugging a production-like issue, learning infrastructure, or working outside comfort zone.
- Strong framing: "I did not own Kubernetes, but I knew enough to gather evidence and help platform engineers narrow the problem."
